browser infrastructure

Lease a real browser on hardware you already own.

Devdooth seats Chrome on your Mac, Linux box, or Raspberry Pi and hands your agent a standard CDP endpoint. Workers dial out, so nothing on your network needs an inbound port, and browser profiles never leave the machine.

Why Devdooth

A browser pool that lives on the machines and accounts you already use.

🔌

Outbound-only workers

Workers need no inbound network port. NAT and firewalls stay exactly as they are.

🧭

Standard endpoints

Each lease is a browser-level CDP WebSocket. Ordinary Playwright, Puppeteer, or any CDP client connects unchanged.

🗂️

Profiles stay local

Named profiles live on the worker and persist across leases. Log in once, reuse it later.

🎯

Capability routing

Request by node, browser, profile, or headful capability. Hard filters, then least-loaded selection.

🤝

Composes, never reinvents

Devdooth does not implement a DOM agent. It leases browsers and hands them to tools that do.

🛡️

Honest security model

Loopback-bound debug ports, hashed device tokens, per-lease credentials, worker-enforced TTLs.

How it works

The coordinator is a control plane and a relay. It never parses CDP traffic.

Agent or Playwrightleases over HTTP, then speaks CDP
→
Coordinatornode registry, leases, scheduling, auth, relay
←
Workerlaunches Chrome, loopback debug port, local profile, outbound tunnel

A worker opens one outbound control WebSocket. When a lease is requested, the coordinator reserves capacity, the worker launches a browser, and a second outbound tunnel carries CDP frames between the caller and that browser. Message type and boundaries are preserved; a slow consumer is dropped rather than buffered without limit.

A profile that persists

Sites that aggressively challenge automation are left alone. Devdooth is not an anti-bot or CAPTCHA-bypass product; it simply uses the network and profile of the machine you chose. Some sites still refuse headless Chromium regardless of IP, and those are not shown here.

Quickstart

Three steps: start a coordinator, enroll a machine, lease a browser.

1 · Coordinator

# on a host with a reachable address
devdooth coordinator --addr :8080 --store devdooth.db
# prints a generated admin token once

2 · Join a machine

# mint a single-use enrollment token on the coordinator host
devdooth enroll-token --url http://localhost:8080 --token <admin-token> --label macbook

# on the Mac / Pi / Linux box
devdooth join --coordinator http://192.168.1.10:8080 \
  --enroll-token <enrollment-token> --name macbook

devdooth worker --coordinator http://192.168.1.10:8080 --profiles shopping,work

The device identity is stored on the worker, so restarts need no token. The coordinator keeps only a hash. Inspect or revoke devices with devdooth devices.

3 · Lease and drive

devdooth lease --url http://192.168.1.10:8080 --token <admin-token> \
  --profile shopping --headful --ttl 1800
# → ws://192.168.1.10:8080/v1/lease/lse_x/cdp?token=...
# Python
async with async_playwright() as p:
    browser = await p.chromium.connect_over_cdp(session.endpoint)
    page = browser.contexts[0].pages[0]
    await page.goto("https://example.com")
// Node
const browser = await chromium.connectOverCDP(session.endpoint);
const page = browser.contexts()[0].pages()[0];
await page.goto('https://example.com');

session.endpoint stands for the endpoint printed by devdooth lease. There is no SDK yet: copy that value (or set it in your own variable) and pass it to your CDP client.

Use it from an AI agent

Devdooth ships no browser tools of its own. devdooth mcp leases a browser, starts upstream Playwright MCP against it, and releases the lease when the MCP server exits. The default launcher runs npx -y @playwright/mcp, so Node.js (with npx) must be available where the MCP client runs. 

// MCP client config (Claude Code, Cursor, VS Code, …)
// run `command -v devdooth` to get the binary path
{
  "mcpServers": {
    "devdooth": {
      "command": "/absolute/path/to/devdooth",
      "args": ["mcp", "--url", "http://192.168.1.10:8080", "--token", "<admin-token>",
               "--node", "macbook", "--profile", "shopping", "--headful"]
    }
  }
}

Then ask the agent to browse. The browser it drives is running on your Mac, using that profile's logins and that machine's network. 

# or point any CDP-aware library straight at a lease
from browser_use import Browser
browser = Browser(cdp_url=session.endpoint)

Using a coding agent to set things up? Point it at AGENTS.md — it has a copy-paste task that builds, starts, leases, and verifies.

Persistent profiles

  • Profiles live at ~/.devdooth/profiles/<name> on the worker (--data-dir overrides the location).
  • One profile is opened by at most one browser at a time; a second request fails explicitly.
  • Profile data stays on its worker and is never copied between machines. A profile-only request matches any online worker advertising that name; pass --node with --profile to pin a specific machine.
  • Complete a login or MFA once in headful mode, and later leases reuse it.
devdooth worker --coordinator ... --profiles shopping,work

devdooth lease --url http://192.168.1.10:8080 --token <admin-token> \
  --node macbook --profile shopping --headful
# cookies and localStorage survive release and re-lease

Security model

A leased browser may be logged into your email, bank, or internal services. Devdooth treats raw browser access as the powerful capability it is.

What it does

  • Outbound-only workers; the browser's debug port binds to loopback.
  • Separate admin and worker credentials. Equal-length admin/static-worker tokens are compared with a full scan; enrolled device tokens are authenticated by hash lookup.
  • Single-use, expiring enrollment tokens; only hashes stored.
  • Per-lease credentials bounded by the lease TTL.
  • Worker enforces the TTL even if the coordinator is gone.
  • Bounded buffers; stalled peers are disconnected.
  • The relay never logs CDP payloads. Normal lifecycle logs omit credentials; development startup and credential-recovery paths deliberately print a token so it is not lost.

What it will not do

  • Protect you from a compromised coordinator.
  • Make an authorized CDP client safe: it can read local files and reach local-network services.
  • Treat CDP filtering as a security boundary.
  • Share one coordinator safely across untrusted owners (single-owner V1).

For real isolation, run workers under a separate OS account, container, or VM, and only expose the profiles you are willing to lend. Terminate TLS at a reverse proxy for non-local deployments and set --public-url https://….

Limitations

  • Chromium-family browsers only (CDP).
  • One browser process per lease; no multi-context packing.
  • Single owner; no ACLs.
  • Workers use installed browsers; Devdooth downloads none.
  • Human take-over is cooperative (pause/resume), not enforced ownership.
  • Remote uploads and downloads vary by browser; verify them per use case.
